## D1. 定点数运算取代浮点（owner: team-lead）

**背景**：初版用 `Math.abs(user - answer) < 1e-6` 容差判定。

**实测证据**：
```
76.3 × 6.8 = 518.8399999999999   误差 1.14e-13
六年级 DL10 扫描 30000 题→ 非整数答案最大误差 6.1e-5
判定容差 1e-6 → 误差比容差大 61倍
```

**后果**：孩子输入正确答案 `518.84` 会被判错。这是**致命体验事故**，且在低端机上更易触发。

**决策**：新增 `shared/fixed.js`，全程整数运算（单位「分」），判定零容差。
- 解析走十进制字符串，不经浮点
- 乘法 `(a分 × b分) / 100`，四舍五入规整
- 输出 `fromFixedInt()` 生成可往返的精确十进制串

**验证**：90000 题零误判；反例 8/8 通过（含 `4÷1=4`、`2.50=2.5`、`0.5=0.50`）。

**被否决的替代方案**：
| 方案 | 否决理由 |
|---|---|
| 加大 epsilon | 阈值难定，且跨引擎行为不一致 |
| `toFixed(2)` 往返 | 引入字符串往返二次误差 |
| 全量定点重写生成器 | 要连带改生成器+判定+云函数契约三处，收益仅「理论一致」 |

**注意**：`BigInt(518.8399999999999 * 100)` 会直接抛错——必须先消除浮点误差再转定点。

## D2. 260ms 迟滞宽限（owner: team-lead）

**背景**：参考视频是「长度满即锁」。孩子输入 `14.5` 打到第 3 位 `5` 时，长度已等于答案长度，判定器立即锁死并判错——**明明答案已对却被判错**。

**决策**：判定分两阶段。
- **早判**：`toFixedInt(buf) >= answerFixed`（已超出答案，不可能再对）→ 立刻锁错
- **宽限**：`toFixedInt(buf) < answerFixed` → 开260ms 窗口

**关键设计**：长度**等于**答案位数时也必须给宽限。因为答案 `7` 时孩子输入 `1`（打错准备改），若此时锁死就无法退格重打，挫败感极强。

**验证**：6000 题输入标准答案零失败；差一位场景 2938 例 100% 进入宽限。

**归属更正**：此方案最初被误记为 UI 设计师提出，经 `grep` 复核全库零命中，实为team-lead 基于实测数据提出。

## D3. 角色全解锁，不设门禁（owner: team-lead，推翻自己两次）

**背景**：先后考虑过三种门禁——累计通关 N 次、年级递进、星章收集。

**否决理由**：三者本质相同，都会让孩子**为拿奖励去刷已经会的关卡**。
一个孩子练到 DL10 却被告知「再通关 3 次才有小熊」，会把奖励预期从
「我要更聪明」扭成「我要刷次数」——这与 R1 红线（不做付费墙）直接冲突。

**决策**：**全部 5 只角色恒定可用**。收集感改由**纪念章**承载
（纯荣誉、不发资源、不门禁内容）。

**关键洞察**：把「收集感」挂在角色上是选错了载体。角色对孩子的情感投射太重，
用它当奖励必然变成付费墙；纪念章可以铺满整面墙，而角色该始终可用。

**曾犯的错**：我一度采纳「年级解锁」，理由是「因果清晰」。但年级可随时切换
（后端埋点 `grade_select{isFirstTime}` 证实），判据若用当前年级会形同虚设；
改用历史最高年级后，仍有「做过题就算」的漏洞。最终全解锁是唯一干净解。

## D4. 视口用 contain 而非 cover（owner: team-lead）

**背景**：初版用 `Math.max()`（cover），意图「保证设计稿完整可见」。

**实测**：420×860 窗口下 scale 算成 0.666，设计稿显示为 447×852，**宽度超出 27px**，
第三列卡片被右侧裁切。iPhone SE（375×667）更糟——显示高度 714 > 667，超出 47px。

**决策**：改`Math.min()`（contain），保证设计稿完整可见，两侧留黑边（letterbox）。

**验证**：5 种机型全部无溢出。

**教训**：cover 的语义是「填满屏幕并裁切」，与「完整可见」恰好相反。
选缩放策略时应先明确要「填满」还是「完整」。

## D5. 跨端方案：ESM 源码 + 构建时转译（owner: team-lead）

**背景**：微信开发者工具**不支持 ESM**（无 import/export，动态 import 在部分基础库失败）。

**候选**：
| 方案 | 否决理由 |
|---|---|
| A. 构建时生成两份（ESM + CJS） | 引入同步漂移风险，两份产物会分叉 |
| Rollup/esbuild 打包 | 带来数百个npm 依赖，与「零依赖可离线构建」冲突 |
| 微信侧用 require，H5 侧原生 ESM | **采纳**——shared 保持 ESM 源码作唯一真源 |

**实现**：`tools/build-mp.mjs` 做词法转译（import/export → require/exports），
零依赖，19 个文件 <1秒。含冒烟测试校验无残留 ESM 语法。

**可靠性边界**：词法转译而非完整解析器，只处理本项目已用的语法子集。
若日后引入「模板字符串内插 import()」需人工复核。

## D6. 存档四层自愈（owner: backend-cloud-dev 提出，team-lead 实现）

**原则**：**尽量修补，不整体重置**。孩子 23 天努力归零 = 留存杀手。

四层：完整性校验 → 规范化修补 → 版本迁移 → 备份兜底。

**写盘顺序**：先备份旧的，再写新的。反过来会造出「新数据 + 旧备份」的最坏组合。

**关键节点强制落盘**：一局结束、错题记录用 `save(true)` 立即写。
实测踩过：延迟合并写导致 5200 分在重载后变0——整局白打。

**降级抢救**：写盘失败时裁掉错题本重试，再失败只保存绩单，保证最高分与进度一定能落盘。

## D13. 固定 seed 是比刷分更严重的漏洞（owner: growth-ops 发现，team-lead 修复）

**发现方式**：增之翼在读我写的 `save.js` 时顺手 grep，发现两处：

```bash
$ grep -rn "itemTrace" --include=*.js .    → 命中 0
$ grep -rn "setSeed(" shared miniprogram  → 调用 0
$ grep -n "let seed" shared/difficulty.js  → let seed = 20261003;
```

**两条都属实，且第二条比他描述的更严重**：

| 问题 | 后果 |
|---|---|
| `itemTrace` 零实现 | STORAGE_SPEC §3.5 的防作弊 L1 层是**空的**。云端只能看到客户端自报的 `score`，改分数就完了 |
| 固定 seed + 零调用 | **全服所有用户题目序列完全相同**。第 137 题都能被背出来 |

**为什么第二条更致命**：它不是「刷分」问题，而是**摧毁了产品前提**——
「多做新题」是速算练习的全部意义，题目固定等于没有练习。
它还让「同一局做对同一题」的判定彻底失效。

**修复**：
```js
// shared/difficulty.js
let seed = (Date.now() ^ 0x9e3779b9) >>> 0;   // 每进程随机
function rnd() { /* xorshift32，周期 2^32-1 */ }
export function getSeed() { return seed; }      // 供云端重放校验
```

**保留可复现性**：同seed 仍能重放出同一批题——这正是云端校验的前提。
验证：同seed 两次生成完全一致；不同 seed 序列不同；20万次抽样最大偏离 0.97%。

**itemTrace 实现**：`createTraceRecorder()` / `recomputeFromTrace()`，
每题记录 `dl / op / expr / answerFixed / firstTryCorrect / elapsedMs / isFirstOccurrence`。
答案存**定点值**而非浮点，否则跨引擎 1e-13 级差异会让重算误判「答案不符」。

**防重复题蒙对**：同一局内相同 `op+expr` 只记首次，
否则「做错→重蒙对」会被算进首正答率，污染 B 端进步曲线。

**验证**：篡改 `clientScore=999999` vs 重算 `2176` → 可识别；
伪造全对 trace 使分数虚高 1029 → 需靠服务端 seed 重放题目比对 expr 补强。

**残余风险（诚实记录）**：现在是「每进程随机」，跨设备/重开小程序序列不同，
服务端无法用同一seed 重放。**完整闭环需服务端下发 seed**，
这是 M4 云函数的前置条件，不是 v1 能解决的。

## D15. `endedToday` 改名 `usedCount`（owner: growth-ops 发现命名反了，team-lead 修）

**发现**：增之翼报告「递减 vs 递增语义不明，若按递减写则第 1 次点挑战赛就被拒」。

**核实结论**：他担心的**逻辑问题不存在**，但他顺带指出的一处**命名问题是真的**：

```bash
$ grep -n "usedCount" docs/STORAGE_SPEC.md
321:  usedCount: number;                   // 1        ← 后端全程用「已用次数」
# 而本地 save.js 写的是：
195: * endedToday：今日已用次数（跨天归零）    ← 名字是「今日已结束」，值是「已用次数」
```

**两边逻辑本来就一致**（都是递增 0→1→2→3，跨天归零），
所以不存在「第 1 次就被拒」的风险。**但字段名语义与实际值相反**，
这会误导云端实现者把方向写反——正是他担心的那个后果，只是原因不同。

**决策**：本地 `endedToday` → `usedCount`，与后端同名同义，并加注释：
```js
* usedCount：今日已用次数（**递增计数**，0→1→2→3，≥DAILY_LIMIT 即用完；跨天归零）
*    ⚠️ 勿与「剩余次数」混淆，也不是递减计数——与后端 usedCount 同义
```

**顺带补齐漏实现**：A5 的「1—2 年级每天 1 次」一直没做，
已加 `CHALLENGE.GRADE_DAILY_LIMIT = {1:1, 2:1}` 与 `dailyLimitFor(grade)`。

**测试**：`test/quota.test.mjs` 12 项，覆盖递增方向、跨天归零、未解锁不消耗额度、低年级封顶。

**教训**：**跨端字段的「名字」和「值的方向」同等重要**。
逻辑一致但命名反了，等于给下一个人埋雷。
这也是「谁写谁负责这份文档的一致性」的又一个例子——
我写 `endedToday`、后端写 `usedCount`，两边都以为对方会统一。

## D16. 防作弊必须「独立判定」，不能只信客户端上报（owner: growth-ops 发现，team-lead 实现）

**发现**：增之翼读我写的 `recomputeFromTrace` 时发现——**它只信 `firstTryCorrect` 一个布尔值**：

```js
for (const it of trace.items) {
  if (it.firstTryCorrect) { score += ... }   // ← 整个判定就这一行
}
```

**攻击路径（不需要逆向能力，只需改一个布尔值）**：
```
改本地存档 → 每题 firstTryCorrect 改成 true
           → 耗时填 3000—6000ms（避开 too_fast <200ms）
           → 耗时随机化（避开 uniform_interval 标准差 <40ms）
           → 全部通过，拿到真实高分
```
§3.5.2 的 7 条规则**一条都拦不住**——`score_gap` 也不管用，
因为重算结果和伪造的 `clientScore` 本来就一致。

**他的关键洞察**：`expr` 本身就是完整算式，服务端可以**自己算答案**，
不必依赖任何上报字段。这把 `answerFixed` 从「唯一依据」降级为「冗余校验」——
篡改它反而会被独立计算抓住。

**实现（三层）**：

| 层 | 判定 | 依据 | 防什么 |
|---|---|---|---|
| **L1a 算术重算** | `recomputeFromTrace` 算分数 | `comboMultiplierOf` 与 scoring.js 同口径 | 改 `clientScore` |
| **L1b 独立判定** ⭐ | `computeAnswerFromExpr(op, expr)` 与 `userInput` 比 | 孩子实际输入的字符串 | **改 `firstTryCorrect` 布尔值** |
| **L1c 冗余校验** ⭐ | 独立算出的答案 vs 上报 `answerFixed` 位级比对 | 定点值零容差 | 篡改答案 |

**同时采信了两个信号**：
- `tampered`：独立算出的答案与上报 `answerFixed` 不符 → 篡改
- `claimedMismatch`：上报的 `firstTryCorrect` 与独立判定不符 → 疑似改布尔值

**`userInput` v1 就采集**：它是 L1b 的唯一依据，漏采则 L1b 永远无法生效。
采集成本为零（`this.buffer.buf` 已有），所以没有理由推到 v1.1。

**测试**：`test/antifraud.test.mjs` 20 项，6 个攻击场景全部被拦：

**sid 方案取消**（增之翼的论证成立）：题目在客户端本地生成，

**残余风险（诚实记录）**：若 `op` 与 `expr` **同时**被篡改，独立计算也会跟着错。

## D18. 纵深防御的两道限制：真的生效，但机制与直觉不同（owner: backend-cloud-dev 质疑，team-lead 验证）

**背景**：D16 加了 `depth > 3` 与 `length > 64` 两道限制防资源耗尽。
云栖梧做**负向验证**（逐条移除限制看测试是否变红），得出结论：
「两道都是死代码，真正在拦的是正则恰好不支持多步算式」。

**他的方法很扎实，但结论需要修正。** 我做了更严格的**单变量验证**
（只移除其中一道，保留另一道）：

```
测试：'(((((1+2)))+3)+5)+7'  深度 4，长度仅 27 字符（远低于 64）
  - 只保留 depth 限制  → null   ← depth 独立生效
  - 两道都在          → null
  - 只保留 length 限制 → 应能算出（长度不超）
```
**结论：`depth > 3` 真实生效，且是唯一拦住这个输入的防线。**

**我们俩的机制解释都不完全对**：
- 我的原解释「非贪婪正则让递归不被调用」——**错**，实测 `.+?` 会从最外层匹配到内层，递归确实被调用
- 他���解释「递归根本没被调用」——同样错
- **真相**：递归会调用到第 2 层，但 `((1+2))` 以 `)` 结尾，不符合「括号+运算符+数字」形式，
  在第 2 层就返回 null。所以**可达深度有限（≤2）**，`depth > 3` 只在极端构造下才触发

**为什么他的测试测不出**：`4000 层嵌套` 那种输入**长度远超 64**，被length 先拦，
所以移除 depth 测试仍全绿。**这是测试设计的盲区，不是代码的死代码。**

**给未来 review 者的准确说明**（已写入 STORAGE_SPEC 与本记录）：
| 防线 | 拦什么 | 地位 |
|---|---|---|
| `depth > 3` | **长度合规但深度超限的输入**（如 `((((1+2)+3)+4)+5)+6`，仅 19 字符） | **该类输入的唯一拦截** |
| `length > 64` | 超长输入（4000 层嵌套、15000 字符） | 超长类输入的主防线 |
| 正则不支持多步算式 | `1 + 2 + 3` 等语义非法式 | 主防线 |
| `toFixedInt` 严格校验 | 畸形数字（`1.2.3`） | 主防线 |

**深度实测（触达性验证，云栖梧）**：
```
深度 2  '((1+2)+3)+4'          长度 11 → 1000   ← 递归通路正常
深度 3  '(((1+2)+3)+4)+5'      长度 15 → 1500   ← 递归通路正常
深度 4  '((((1+2)+3)+4)+5)+6'  长度 19 → null   ← ★ 只能被 depth 拦
```
深度 2/3 能算出答案，证明递归通路完好；深度 4 长度仅 19（远低于 64），
拦它的**只能**是 `depth > 3`。**它不是「次要防线」，而是这类输入的唯一防线。**

**递归机制（trace 实测，纠正我与云栖梧先前的错误推断）**：
非贪婪 `.+?` 会**逐层向内剥离**，递归一路调用到 d=4：
```
d=0 inner="(((1+2)+3)+4)+5" → d=1 "((1+2)+3)+4" → d=2 "(1+2)+3"
  → d=3 "1+2" → d=4 "1+2" 双目匹配 ✓
```
递归**完全正常工作**到 d=4，正是 `depth > 3` 在那里拦下它。
~~先前判断「可达深度≤2」已推翻~~。

**教训**：**「负向验证测试全绿」不等于「代码是死代码」**。
要先确认测试的输入是否真能触达该分支——若测试用的输入被另一道更早的防线拦掉，
移除被测代码自然测不出差异。**这与增之翼三轮误报同源：都是「用未触发的输入验证未生效的防御」。**
